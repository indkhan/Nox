# Spikes 0.2 + 0.5 — Codex via app-server

**Date:** 2026-08-21 · **Scripts:** `spikes/codex-full.mjs`, `spikes/codex-latency-image.mjs`
**Binary:** `codex` **0.149.0**, resolved deliberately via `bridge/resolve-codex.mjs` — the first
run used the wrong one and got misleading results (see the binary-resolution hazard below)

## 0.2 `dynamicTools` round trip — **PASS**

The architecture holds. Codex called back into the client and used our answer.

```
→ thread/start { dynamicTools:[notion_fetch], model, effort:low, ephemeral:false,
                 sandbox:'read-only', approvalPolicy:'never', personality:'pragmatic',
                 developerInstructions:'You are Nox…' }
→ turn/start   "What is the status of Notion page 1a2b3c…?"

⇐ item/tool/call  tool=notion_fetch ns=null args={"page_id":"1a2b3c4d5e6f7890abcdef1234567890"}
⇒ { success:true, contentItems:[{type:'inputText', text:'{"title":"Second Brain","status":"In Progress","owner":"Usman"}'}] }

⇐ agentMessage: "The Notion page "Second Brain" is In Progress and owned by Usman."
```

Everything the design depends on is confirmed:

| Claim | Result |
|---|---|
| Codex requests client-side tools via `item/tool/call` | **yes** — with the tool name and correctly extracted arguments |
| The client's returned result reaches the model | **yes** — the answer quoted our fake title, status and owner |
| Item stream is renderable | **yes** — `userMessage, dynamicToolCall, agentMessage`. `dynamicToolCall` is the action-stream row |
| `developerInstructions` overrides the coding-agent persona | **yes** — behaved as a Notion assistant with no filesystem |
| `sandbox:'read-only'` + `approvalPolicy:'never'` accepted | **yes** — no shell or patch approvals were ever requested |

**Nox keeps the agent loop.** Approvals, the action stream and undo all remain ours.

## Web search — **PASS**

Enabled by default; no config needed.

```
items: userMessage, reasoning, webSearch ×5, agentMessage
answer: cited https://formulae.brew.sh/… and https://getroutines.ai/…
```

**UI caveat:** the `webSearch` item carries an **empty `query`** and `action:{type:'other'}`:

```json
{"type":"webSearch","id":"ws_0f80…","query":"","action":{"type":"other"}}
```

So the progress row can say *"Searching the web"* and a count, but **not** *"Searching for X"*
the way Notion AI does. Cosmetic, but it changes what E5 can render.

## 0.5 Latency and models

**First run was measured against the wrong binary.** `spawn('codex')` resolved via PATH to the
desktop app's **0.143.0**, whose `model/list` returns only `gpt-5.5`, `gpt-5.4`, `gpt-5.4-mini` and
which 400s on the account's actual default. Re-run against the npm-vendored **0.149.0**, the
account exposes six:

| Model | First token | Total | Notes |
|---|---|---|---|
| `gpt-5.6-sol` | 3038 ms | 3139 ms | **account default**; OpenAI's flagship tier |
| `gpt-5.6-terra` | 2688 ms | 2788 ms | balanced tier |
| `gpt-5.6-luna` | 3287 ms | 3400 ms | positioned as fastest/cheapest |
| `gpt-5.5` | 2407 ms | 2523 ms | |
| `gpt-5.4` | 2574 ms | 2704 ms | |
| `gpt-5.4-mini` | 4418 ms | 4551 ms | |

**Do not pick a default from this table.** Every model lands within ~2 s of the others on a trivial
prompt, and the ordering doesn't match OpenAI's own positioning (Luna is billed as the fastest yet
measured mid-pack). That spread is round-trip overhead, not model speed — the numbers only separate
on real work.

**Design consequence: Nox does not choose a model.** `model/list` returns `displayName`,
`description`, `inputModalities`, `supportedReasoningEfforts` and `serviceTiers` for each entry —
everything a picker needs. Render them all, mark the account default, let the user decide. New
models then appear without a Nox release.

Realistic turns, for expectation-setting:

- one tool call + answer: **9.2 s**, first token at 8.5 s
- web search turn: **26.3 s**

**This is the product risk, quantified.** Notion AI feels instant; ~9 s with one tool call is a
different experience. Streaming reasoning summaries early is what makes it tolerable — E5 should
render the progress row the moment `turn/started` arrives, not on first text.

## Image input — **PASS**

`UserInput` accepts `{ type:'image', url: <data url> }`. A generated 16×16 solid blue PNG passed
as a base64 data URL was correctly identified ("Blue", 3.4 s). No temp file needed, so browser
attachments can go straight through.

`UserInput` variants worth knowing: `text`, `image` (url), `localImage` (path), `audio`,
`localAudio`, `skill`, `mention`.

## `cwd` — must be set explicitly

| thread/start | resulting `thread.cwd` |
|---|---|
| `cwd` omitted | `C:\codebases\Nox` — **inherits the app-server process's cwd** |
| `cwd: <temp dir>` | `C:\Users\…\Temp` — **honoured** |

Omitting `cwd` does not mean "no directory"; it means "whatever directory the browser happened to
launch the bridge from". **The bridge must pass an explicit, non-writable directory.**

## `ephemeral` — the privacy switch works

- `ephemeral: false` → `thread.path` is a real `~/.codex/sessions/…/rollout-*.jsonl`
- `ephemeral: true` → **`thread.path` is `null`, nothing written to disk**

So the "keep Notion content out of `~/.codex`" option is genuinely available if we ever want it,
at the cost of replaying history each turn. Current decision remains persistent (MVP §5).

## Hazard: `spawn('codex')` is ambiguous — resolve the binary deliberately

Three `codex` binaries coexisted on this machine, and they are **not** interchangeable:

| Version | Path |
|---|---|
| **0.149.0** | `…/nodejs/node_modules/@openai/codex/node_modules/@openai/codex-win32-x64/vendor/x86_64-pc-windows-msvc/bin/codex.exe` |
| 0.143.0 | `…/AppData/Local/Programs/OpenAI/Codex/bin/codex.exe` (desktop app) |
| 0.143.0 | `~/.codex/packages/standalone/releases/0.143.0-…/bin/codex.exe` |

`codex --version` in a shell printed **0.149.0** (the npm launcher resolving to its vendored
binary), but `spawn('codex')` from Node resolved through PATH to the **desktop app's 0.143.0**.
Symptoms of running the old one:

- `model/list` hides every `gpt-5.6` model
- the account default 400s: `"The 'gpt-5.6-sol' model requires a newer version of Codex."`
- persistent stderr: `failed to load models cache: missing field base_instructions`

All of which look like Nox bugs.

**Fix, implemented:** `bridge/resolve-codex.mjs` enumerates candidates (npm-vendored platform
package, `CODEX_BIN`, desktop app, cached standalones, PATH last), runs `--version` on each, and
picks the newest. Verified: chooses 0.149.0 and correctly reports the PATH entry as 0.143.0.

**For E3:** use the resolver, never bare `codex`; report the running version from
`initialize.userAgent`, never `codex --version`; and if the user's chosen model isn't in
`model/list`, say the binary is out of date rather than forwarding a raw 400.
