# Spike 0.2 — driving `codex app-server` with client-supplied tools

**Date:** 2026-08-20 · **Machine:** Windows 11, codex shim 0.148.0 → standalone **0.143.0**
**Script:** `spikes/codex-dynamictools.mjs`

## Verdict: PROMISING, not yet conclusive

`dynamicTools` is accepted and the whole thread configuration works. The one thing still unproven
is the `item/tool/call` round trip, blocked by the account's Codex usage limit — **an account
state, not an API rejection**. Re-run after the quota resets to close it out.

## Proven

| Finding | Detail |
|---|---|
| Protocol | JSON-RPC over stdio JSONL with **no `jsonrpc` field on the wire**, exactly as documented. `initialize` → `initialized` → requests. |
| `experimentalApi` | Accepted in `initialize.capabilities`. |
| **`dynamicTools` on `thread/start`** | **Accepted, no error.** The type surface exists in this build: `DynamicToolSpec`, `DynamicToolFunctionSpec {name, description, inputSchema, deferLoading}`, and server request `item/tool/call` with `DynamicToolCallParams {threadId, turnId, callId, namespace, tool, arguments}`, answered with `DynamicToolCallResponse {contentItems[], success}`. |
| Tool results can carry images | `DynamicToolCallOutputContentItem` = `inputText` \| `inputImage` \| `inputAudio`. |
| Thread configuration | `developerInstructions`, `personality`, `sandbox: "read-only"`, `approvalPolicy: "never"`, `model`, `effort`, `ephemeral` all accepted on `thread/start`. Note the field is `developerInstructions`, **not** `collaborationMode.settings.developer_instructions` as the `main` README describes. |
| Model catalog (this build) | `gpt-5.5` (default), `gpt-5.4`, `gpt-5.4-mini`. All `text,image`. Efforts `low/medium/high/xhigh`. `gpt-5.5` advertises a `priority` service tier ("Fast", 1.5x speed). |
| **Persistence confirmed** | With `ephemeral:false`, a rollout file appears immediately at `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl` — **48–52 KB even for a turn that failed before producing output**. RESEARCH §3.6 is correct. |
| **`cwd` defaults to the process cwd** | We passed no `cwd` and the thread came back with `cwd: "C:\\codebases\\Nox"`. The bridge **must** pass a controlled directory, or Codex inherits whatever the browser launched it from. |
| Quota error shape | `codexErrorInfo: "usageLimitExceeded"`, message `"You've hit your usage limit... or try again at 10:26 PM."` Exactly what the health check should surface. |
| Unsupported-model error shape | `400 invalid_request_error` — `"The 'gpt-5.6-sol' model requires a newer version of Codex."` |

## Not proven

- **`item/tool/call` round trip.** The turn never reached the model (quota). Until this is seen,
  it remains possible that `thread/start` accepts `dynamicTools` and silently ignores it.
  `ThreadStartParams` in the generated bindings does **not** list `dynamicTools`, so it is being
  accepted as an untyped extra field — which is consistent with both "experimental, works" and
  "ignored".

## Hazard found: version skew

Four `codex` entries on PATH:

```
C:\Users\mgsuk\AppData\Local\Programs\nodejs\codex          → prints 0.148.0
C:\Users\mgsuk\AppData\Local\Programs\OpenAI\Codex\bin\codex.exe
C:\Users\mgsuk\.codex\packages\standalone\releases\0.143.0-x86_64-pc-windows-msvc\bin\codex.exe
```

The npm shim reports 0.148.0 but delegates to the **0.143.0** standalone, which is what
`app-server` reports in `initialize.userAgent` and `thread.cliVersion`. Consequences:

- The account's default model (`gpt-5.6-sol`) is newer than the running binary supports, so a
  default-model turn fails with a 400 that looks like a Nox bug.
- `model/list` returns only what the running binary knows, not what the account has.
- A stderr warning appears on startup: `failed to load models cache: missing field base_instructions`.

**Implications for E3:** the bridge must resolve and record the *actual* binary and version, pin an
explicit `model` rather than relying on the account default, and surface a version-skew warning
rather than passing a raw 400 to the user.
