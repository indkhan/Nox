# Spikes 0.1, 0.3, 0.4 — from the extension harness

**Date:** 2026-08-20 · **Machine:** Windows 11, Chrome · extension id `mocebdbngeojcjenigojedapolmpafeo`

## 0.1 Notion OAuth from a real extension — **PASS**

Full chain verified end to end:

```
discovery → DCR (client_id 6OsmcBnNP6c4kmPs) → PKCE S256 → launchWebAuthFlow
→ consent → chromiumapp.org/?code=… → token (workspace 143c50f2…, expires 28800s)
→ MCP initialize ok — protocol 2025-06-18
```

**But it failed first, and the reason matters.** The initial attempt died at `initialize`:

```
403 {"code":-32000,"message":"Invalid Origin: mocebdbngeojcjenigojedapolmpafeo"}
```

`mcp.notion.com` runs an **Origin allowlist on authenticated requests** and rejects
`chrome-extension://` origins. The check sits behind auth, so unauthenticated probing never
reveals it — the earlier `curl` research saw a clean CORS preflight and a `401`, and wrongly
concluded no proxy was needed anywhere. RESEARCH §2.1 has been corrected.

**Fix:** strip `Origin` with a `declarativeNetRequest` dynamic rule keyed on
`initiatorDomains: [chrome.runtime.id]` and `requestDomains: ['mcp.notion.com']`. `Origin` is a
forbidden header, so `fetch()` cannot do it. Confirmed working.

**Carry into E2:** the DNR rule is load-bearing. If it ever stops applying, the fallback is to
route MCP through the native bridge, where Node sends no `Origin`.

## 0.3 The 1 MB native-messaging ceiling — **PASS**

```
raw 2 MB      → "Error when communicating with the native messaging host."
chunked 2 MB  → 4 chunks, 2,097,152 chars sent, 2,097,152 reassembled
```

Reproduced twice, and independently in `bridge/test-bridge.mjs` outside Chrome. The cap is real,
the failure is an opaque port teardown with no useful error, and the framing design handles it.
**Chunking is mandatory, not defensive.**

Side observation: each `connectNative` spawned a fresh host process (pids 22740, 23060, 7416,
5344). Fine for a spike; E3 must hold **one** long-lived port instead of reconnecting per call.

## 0.4 Panel lifetime — **PASS**

With the panel enabled **globally** (not per-tab):

- **Switching tabs with the panel open → the document survives.** `alive for` keeps climbing, so
  an in-flight turn is not interrupted by normal browsing.
- **Closing the panel → the document is destroyed**, timer resets to 0.

The first is what mattered; the second is the behaviour the design already assumes. The earlier
`loaded 2 times` reading was extension reloads, not tab switches.

**Decision: the agent loop lives in the side panel document.** No offscreen document needed, which
removes a whole component from E1/E8 and avoids Chrome's justification prompt for long-lived
offscreen documents.

**Consequence to keep honest about:** closing the panel ends any running turn or bulk job. Already
covered — the journal is in IndexedDB, so reopening shows an interrupted-turn banner with what
changed and working undo (MVP §6.5, §7).

## Unplanned finding — content scripts were the wrong tool

The harness originally read the current page id from a content script on `notion.so`/`notion.com`.
It reported nothing for an open Notion tab, because **content scripts are not injected into tabs
that were already open when the extension loaded** — every extension reload silently broke page
detection until the user refreshed Notion.

Replaced with `chrome.tabs` (`onActivated` / `onUpdated` / `onFocusChanged` plus a query on
demand), which gives `url` and `title` with no injection, no refresh, and no content script at
all. `extension/content.js` was deleted and `content_scripts` removed from the manifest.

MVP §3 previously described a content script for this; page detection is now entirely in the
service worker. A content script will come back only when text-selection context is needed.
